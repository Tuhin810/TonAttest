01 — The problem

Every team rebuilds the same pipeline, and gets it wrong the same way

A Mini App wants to reward real STON.fi activity — swap 100 TON and earn points, provide liquidity for a week and unlock a perk. Today that means building all of this from scratch:

fetch transactions→ decode contract messages→ match campaign logic→ guard against replays→ detect fake volume→ store eligibility

One to three weeks per app — and each implementation is subtly wrong in the same places. These are not hypotheticals. Each was found by running a decoder against live mainnet data:

The trap What it does if you miss it
Native TON has three on-chain spellings Compared literally, every TON swap fails to match its own pool
LP tokens are transferred, not minted A mint-only decoder sees every liquidity deposit as nothing at all
Native amounts live in a separate field Reading only the jetton field silently drops most swaps on the DEX
Gross volume is free to inflate Swapping back and forth manufactures unlimited qualifying volume

Quest platforms solve the campaign website version of this. Nothing solves the embedded developer primitive version — rules defined in your own code, verified server-side, consumed programmatically.

02 — What it is

A verification service that proves activity, and never touches money

The service reads the chain, evaluates your rule, and signs a statement about what it found. Your app decides what the reward is and pays it from its own wallet. There is no smart contract, no custody, and no token in this design.

03 — How it works

One call, and a proof you check yourself

Step 9 is the one that matters. Your app checks the signature itself, against a public key it pinned at deploy time. A spoofed response, a hijacked DNS record, or a fully compromised verification service cannot mint rewards from your treasury.

That is also why hosted and self-hosted have the same security story — you are never trusting a live response.

Failure is never a wrong answer

If a wallet's history cannot be resolved completely — upstream outage, rate limit, or a history larger than the fetch cap — the service returns a typed 503 rather than evaluating partial data. An under-counted history produces a confident "you don't qualify" for someone who did. A false negative is a support ticket; a false positive is a payout that cannot be reversed.

04 — Using it

Install, define, verify

// npm install @ston-rewards/sdk

import { StonRewards, swap, all, lpHold, verifyAttestation } from "@ston-rewards/sdk";

// 1 — Define a rule. Plain JSON underneath: store it, send it, hash it.
const campaign = await ston.createCampaign({
  name: "Swap 100 TON and hold LP for a week",
  rule: all(
    swap({ minAmount: 100_000_000_000n, token: "TON" }),
    lpHold({ pool: TON_USDT, minDuration: "7d" }),
  ),
  startsAt: new Date(),
  endsAt: new Date(Date.now() + 30 * 86_400_000),
});

// 2 — Ask, from your backend, when the user claims.
const result = await ston.verify({ wallet, campaignId: campaign.id });
if (!result.eligible) return render(result.evidence);

// 3 — Verify offline against a key you pinned, then reward.
const check = await verifyAttestation(result.attestation, PINNED_KEY);
if (!check.valid) return;

await markNonceSpent(nonce);   // before paying, never after
await awardPoints(userId, 100);

The rule language

Rules are composable condition trees, capped at three levels of nesting so evaluation stays bounded and results stay explainable to the person reading them.

Condition Fields
swap minAmount · minVolumeUsd · token · pool · count · window · netVolume
lpAdd minLpAmount · minAmountUsd · pool · count · window
lpHold minDuration (required) · minLpAmount · pool
all / any Combine any of the above, up to three levels deep

Evidence is the trust feature

Every evaluation returns evidence — on failure as well as success. Showing gross volume beside net volume is what makes "but I swapped way more than that" answerable in a single screenshot. 

{
  "kind": "swap",
  "satisfied": false,
  "detail": "counted 62400000 of 100000000 token units",
  "measured": {
    "qualifyingSwaps": 3,
    "volumeTokenUnits": "62400000",
    "grossVolumeTokenUnits": "184000000",
    "netVolume": 1
  },
  "txHashes": ["ae72f139…", "0a708b7d…", "af015ab6…"]
}

Evidence is byte-identical for identical inputs, and its hash is bound into the signed attestation — so a disputed result can be re-derived offline, years later, and checked against the signature.

05 — Anti-abuse

Layered, configurable, and honest about the gap

Attack Defence Default
Wash trading Net volume: bought minus sold, per asset. A round trip nets to ~0 On
Double-counted events One on-chain event counts once, ever — dedup at decode plus a database constraint On
Replayed proofs Single-use nonce and a one-hour expiry; the app records spent nonces On
Double-tapped claims Server-derived idempotency key plus single-flight collapse On
Rapid-fire farming Minimum interval between counted actions, applied before aggregation Opt-in
Whales draining a budget Maximum rewardable volume per wallet Opt-in
Disposable wallets Minimum wallet age floor Opt-in
Multi-wallet Sybil rings Not solved. Bind rewards to a Telegram identity instead Open

The Sybil gap is stated plainly rather than buried. One reward per Telegram user id makes a ring cost one Telegram account per extra claim — which raises the price substantially without pretending to a solution. Graph heuristics come later, and will be described as heuristics.

07 — Delivery

Four phases, cut along risk rather than calendar

Each phase ends in something independently useful. Stop after phase two and what exists is still a working open-source decoder and rule engine — not a half-built service.

Known limitations

Tracked openly in the repository rather than discovered later by an integrator:

Limitation Consequence
Fixture set below target Missing v2 routers, multi-hop routes, and a partial LP withdrawal
USD uses the current rate, not the historical one USD rules are marketing-grade; token-unit rules are dispute-proof
~0.3% of swaps cannot be attributed to a pool Pool-scoped rules will not match them — a deliberate refusal, not a bug
LP token legs are best-effort Pool, LP units and timing are authoritative; the legs are evidence only
08 — Design decisions

The choices a reviewer should interrogate

Why refuse rather than guess?

Chain data reports swaps at router level, so a pool must be inferred from the token pair. When several pools share a pair, the swap is recorded without a pool rather than attributed to a likely one. A false negative is a support ticket; a false positive is a payout that cannot be clawed back. Every ambiguous case in this system resolves toward the former.

Why is the rules engine forbidden from doing any IO?

Because a disputed eligibility answer has to be re-derivable. Evaluation takes an activity set and never fetches, never reads a clock, and never imports the IO packages — a CI test enforces all three. The same rule and activity therefore always produce byte-identical evidence.

Why is net volume counting the default?

Gross volume is inflated by swapping back and forth at near-zero cost. Netting per asset makes a round trip worth roughly nothing, while a genuine one-way position still counts in full. Both figures appear in evidence, so the user can see exactly why the two differ.

Why is a negative result never signed?

A signed "not eligible" would be a durable, transferable statement about a person's wallet, with no upside — and the caller already has the evidence explaining the failure.

Why no smart contract or custody in v1?

Settlement is the integrating app's job. Keeping funds entirely out of this system means a compromise of the verification service cannot move anyone's money, and it removes the audit surface that would otherwise dominate the build. An on-chain settlement contract is a later, optional layer — not a prerequisite for the primitive to be useful.
